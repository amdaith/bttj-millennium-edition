All Channels Open: Multimodal Human-Computer Interfaces

The MUESLI programme

The MUESLI project at Adastral Park has two fundamental aims.

  • To research the design of innovative and effective multimodal interfaces.
  • To investigate the robustness of such interfaces with real users

In order to support these aims, we are building a multimodal advanced spoken language interface to a useful multimedia application, which acts as a research vehicle. We are focusing on human-machine dialogue systems, in distinction to other multimodal work on human-human communication in shared spaces.

Outline of the programme

Neither the technology nor the human factors issues associated with multimodal interfaces are very well understood. We therefore considered it best to proceed in a staged approach, from paper exercises to fully automatic system, as follows.

  1. Storyboarding possible system interactions with a focus group, using pictures of the system's output screen. This is a low-cost, quick and flexible approach which allows a wide range of ideas to be explored, but its disadvantage is that it is very unlike the real system, and may not give accurate user predictions as to what they would like.
  2. Exploring different system designs with a focus group, using a set of pre-canned (but real) output screens (see Focus Groups).
  3. Performing Wizard of Oz (WOZ) simulations of successive versions of the system with a user group (see Realistic Wizard of Oz Simulation).
  4. Constructing a complete trial system, and performing a user trial (see Natural Language Server).

The staged approach has two main benefits. Firstly, it enables us to maintain a user focus, and adapt the system we build to what users find helpful, rather than being purely technology driven. Secondly, the system remains more flexible longer into the programme, and is therefore more useful as a research vehicle for answering our basic questions about multimodality.

Before proceeding to describe stages 2-4 in more detail, we will briefly elaborate on the aims of the project. Our aim is to create a usable system with today's technology, and yet to be creative and innovative. This has meant steering a careful middle course between a flaky over-ambitious system and a solid over-conventional one. One of our fixed points is to have a flexible dialogue (as opposed to prompt and response or template-driven) with fluent speech input and advanced language understanding. One of the main aims of the project is to force us to address the issues of making spoken language technology work with ordinary people in a non-demonstration situation and in a useful application. These issues include recogniser speed, accuracy and noise-robustness, robust parsing and language understanding, and creation of a habitable multimodal interface.

It was very important to choose a suitable application environment. The main requirements were as follows.

  • Suitable scope for a multimodal interface, preferably one in which the different input modalities can be profitably combined on a single input turn. This was thought to suggest a visual scene where a number of objects stand in relation to one another.
  • Areasonably densely populated database or information source, so that the multimodal interface, and particularly the language component, gets a serious test. The database should not be too large, or we will run into problems of speech recognition accuracy. A maximum of about 1000 items at each dialogue state would be best.
  • Clear business potential.

The application chosen was an existing 3D retail system (internal to BT), which met all the above requirements. The application and existing interface with its 2D fabric palette and its 3D virtual world provided a rich environment for developing a multimodal interface. The number of fabrics (about 500) and other elements of the world (furniture, colours, locations, etc) was just what we were looking for. Business interest was high, with e-commerce a fast-growing market. Spoken language provides a clear (assumed) benefit over the existing mouse-driven interface, particularly for the browsing and selection of fabrics, but also in allowing extra functionality and in creating a completely new metaphor for interaction with the system, namely conversing with the virtual assistant.

Focus groups

Stage 2 of the programme was to explore different system designs with focus groups. Each group was shown a demonstration of one incarnation of the system, called the Virtual Showroom, following a scripted scenario, lasting a few minutes. This scenario was created in Macromind Director, a multimedia authoring package. The entire effect was a realistic simulation of what we intended the system to be. This included the appearance of the screen, with the three elements of virtual assistant (the talking head), 2D fabric selection palette and 3D virtual showroom (including animations); the voice used by the talking head; the sorts of user inputs (which were spoken by the demonstrator, and used to trigger the next screen in the script); and the sorts of responses given by the virtual assistant, which included system initiatives such as opinions on the fabrics selected or suggestions as to what the user should buy. The main functionalities demonstrated in the script were fabric selection, transfer of fabric from palette to object in the virtual world, moving objects in the virtual world, navigation round the virtual world, pricing information, and the ability of the system to suggest 'matching' fabrics or fabrics which 'suited' an existing design. The focus group participants would not be very aware of the fact that there was only one path through the dialogue of this system.

The experiment was repeated with 4 focus groups, each containing 12 home-owners in the age range 25-45. Following the demonstration, an experienced experimenter conducted a moderated discussion lasting about 30 minutes to ensure that the following topics were covered.

  • Using the Virtual Showroom - how and where would participants use it, what would invite them into using it, how did they feel about interacting by speech and touch?
  • Virtual Assistant Persona - did participants like the Virtual Assistant concept, did they like the implementation shown, would they trust the Virtual Assistant's suggestions
  • Fabric Selection - how would participants normally select fabrics, what information would they require
  • 'Matching' - how would participants expect the Virtual Assistant to select "matching" fabrics, or choices that 'suit', would they tolerate poor selection choices?
  • Pricing Information - what price information would participants require, and at what stage of the selection process would they want it
  • Other requirements?

The benefit of using focus groups with a simulated system like this is two-fold.

  • It enables the system developers to gain a wide range of user opinion about the functionality and interface as shown, with fairly low cost in development effort. The potential users can talk over a range of possible variants without them all having to be implemented. If desired, the simulation can be modified somewhat at very low cost, and more focus groups run.
  • A number of research issues are thrown up, requiring a series of more carefully targeted experiments to find the answers. These research issues may not be at all obvious before the focus groups.

A potential drawback of the focus group approach is that since the participants are passively watching a demonstration of a system rather than interacting with it, their opinions may be significantly different.

A summary of what we found in the focus groups.

The majority of participants were very positive about being able to plan their own room design, i.e. choose furniture fabrics, wallpaper, curtains, and arrange the furniture in the virtual living room. Most participants initially said that they would be happy to interact with the system using speech, but also raised concerns about privacy and about the capabilities of speech recognition software. They thought that the interaction demonstrated to them involved too much speaking, on the part of both the human user and the Virtual Assistant, and would prefer to rely more on the touch-screen input, which was more familiar to them.

Participants had mixed views on whether the Virtual Assistant was any benefit to the interaction. They consistently disliked the appearance and voice of the Assistant shown in the demonstration (the particular head used looked like a convict), and wanted a more natural human face and voice, with a choice of male or female entity. Participants could readily accept the Virtual Assistant making fabric selections and offering suggestions, but would not accept the Assistant making comments on their taste or attempting to manipulate their choices.

The participants mainly perceived the Virtual Showroom as something that they would access in-store, under the initial guidance of a human sales assistant, and with actual fabric samples available for inspection. (as opposed to Internet shopping from home). They wanted a number of additions to the functionality demonstrated, including;

  • ability to customise the room size, shape and style,
  • full-screen display of fabric samples,
  • better support for browsing samples,
  • more information about fabric weight, texture, durability,
  • different options for the Virtual Assistant persona,
  • improved fidelity of colour reproduction,
  • optional text responses for greater privacy.

The principle issues for further research emerging from the focus groups were:

  • The optimal balance of spoken and non-spoken user input,
  • the optimal quantity and frequency of spoken responses from the Virtual Assistant,
  • the limits on acceptable behaviour from the Virtual Assistant,
  • the limits of trust in the Virtual Assistant,
  • preferred representation of the Virtual Assistant.

Realistic Wizard of Oz Simulation

The third stage of our programme was to use the Wizard of Oz (WOZ) methodology to simulate the system with users. This allows users to interact with what they believe is a real system, without having to create the entire system first. It is a half-way house between the focus groups and the fully automatic trial system. The simulation has become less flexible and more expensive than the scripted scenario, but users' reactions may now be expected to be very similar to those in response to a real system.

We considered it important to simulate the limitations of an automatic system as accurately as possible, including speech recognition errors, grammar limitations, limitations of dialogue understanding, limitations of functionality, etc. This is in distinction to the 'loose' simulations often performed where the wizard gives an almost human-like response. In order to perform such a realistic simulation, it is necessary to define a tight protocol to govern the wizard's response to each user input, and to create a sophisticated wizard control panel to enable the correct system response to be generated and output in near-real time (i.e. a maximum delay of a few seconds). This is no easy task when the system being simulated has a flexible dialogue, a moderately large grammar and domain size, and continuous speech input. The manner in which we achieved this is described in detail in Wyard and Churcher [6].

In the context of the overall MUESLI programme, it is worth noting that the WOZ system is not just a 'smoke and mirrors' mock-up of the system. It is a carefully crafted simulation of a fully automatic system, and it contains a number of components which are reused in the automatic system, such as the response generation module, all the components of the user interface and the communication infrastructure between the user interface and the NL server.

We now give a description of the WOZ system, the experiments performed, and the results obtained.

The Wizard of Oz system comprises three components: a user interface, a wizard response panel and a Natural Language (NL) server.

The user interface (figure 5) is derived from an existing non-speech 3D retail system developed at Adastral Park which allows a user to browse fabrics and then place them on to objects in the virtual world. It consists of two windows; the first shows the Virtual Shop Assistant, which is a 2D talking head developed at Adastral Park and is able to lip-sync and make small facial movements while playing Text-to-Speech from the Laureate TTS system [7], The second window is a World Wide Web browser containing a Java applet which displays a palette containing up to six fabrics along with the fabric name and the class of objects to which the fabric is applicable, and a Superscape Viscape 3D world. The 3D world depicts a scene from a typical sitting room. The sofa and chairs, the curtains and the walls are active and may be touched by the user. The NL server receives touch information from the user interface, determines which objects or fabrics have been touched, and then sends this information to the wizard response panel.



Fig 5. The user interface

The wizard response panel (see the figure 5) comprises four main sub-panels - error response, fabric descriptor, history and function panel. The error response panel contains seven buttons that the wizard can select in accordance with the wizard protocol filter described in detail below. Six fabric descriptors can be used: fabric name, colour, pattern, material, class of object to which the fabric can be applied, and pricing constraints. The wizard is able to type the first letter or two into a descriptor's text box, and a list automatically shows the nearest match.
 

Fig 6. Wizard Response Panel

The history panel assists the wizard in two ways - it records the touches the user makes in the virtual room or on the palette, and also keeps a record of previous interactions. The wizard can thus keep track of the local discourse context and can interpret the user's requests correctly. For example, if the user touches the sofa in the virtual room, the history displays a message showing that the sofa has been touched; it also shows which fabric is currently on the sofa. With a click of a button the wizard can quickly transfer attributes such as the fabric name and colour to the descriptor panel. For example, imagine the user said 'put that on the chair'. The history panel will display the touch event as '11:23:09 User touches sofa (Cartouche Stripe)'. The wizard simply has to click the 'Fabric' button on the history panel, which transfers Cartouche Stripe to the descriptor panel. The user then selects the destination object (chair) and finally triggers the 'transfer fabric' on the function panel. All events are timestamped to assist the wizard in determining the local context.

The wizard's actions send commands to the NL server, which in turn instructs the user interface to change the fabrics displayed on these objects. Future implementations will also allow the server to move objects around in the room and to change the user's viewpoint.

The NL server consists of a number of components: an internal representation of the 3D world, a response generation module, and various database lookup modules. The server is able to return a number of fabrics which meet certain specified criteria, for example within a colour range, of a particular material and so on, but is also able to relax these criteria in a controlled manner so that at least one fabric is returned for each query. These relaxed constraints are passed on to the response generation module. The server also logs all communications between the user interface and wizard panel (such as individual touches by the user on the screen, and functions triggered by the wizard) for transcription and later analysis.

The wizard employs a seven-stage filter which is applied sequentially when assessing whether user input could be processed by the simulated system. The wizard response panel is designed to assist in this mental process by showing a sequence of error buttons corresponding to these stages. If the filter is passed through without triggering an error then the wizard processes the input. The questions the wizard must ask itself are as follows.

  1. Can the user's touch and speech be interpreted as a combined event?
  2. Has the user specified a single query in their request?
    3.
  3. Has the user waited for a response from the system before offering more input?
  4. Is the user's speech clear, with no false starts, hesitations etc?
  5. Is the user's vocabulary and grammar within that of the target system as specified by legal/illegal examples?
  6. Can the user's request be interpreted through context or is it ambiguous/unclear?
  7. Is the user's request outside of the scope of the system's functionality (as per paper specification)?
    8.

The filter illustrates the tight restrictions that are placed on the user input to pass only those which would be interpreted by the target system. In a fully automatic system it might sometimes be difficult to detect which stage has been violated.

Each stage has an associated error response that is automatically generated by the NL server. Currently the response does not take context into account so each generates a single spoken response. Future implementations will make use of more sophisticated response generation techniques, involving context to give more helpful advice. Although the filter is sequential, as the wizard becomes familiar with the protocol, it is able to make a quick assessment without having to go through the filter one error at a time, hence the application of this filter protocol is rapid, allowing a near real-time response from the system.

A laboratory comprising two adjacent rooms divided by a one-way mirror was used for the trials. The wizard sat in the control room and was able to see into the subject room through the mirror. A video camera was erected in the subject room to provide a live 'over the shoulder' view of the user interface and the user's hands as they touched the screen. The video feed was displayed to the wizard on a monitor and was simultaneously recorded directly on to Super VHS. At the same time, a high-quality microphone placed above and to the right of the user's head recorded sound on to DAT. The wizard monitored the sound via headphones. The wizard is assisted by an experimenter in the subject room who outlines the capabilities of the system, acts as timekeeper and conducts a debriefing interview after the trial. As discussed below, the experimenter can provide help to the user, but must avoid priming them. There were 11 subjects, 5 of which were women, and all were recruited from Adastral Park. Hence, the subjects were generally fairly familiar with computers.

To assist in the later transcription of the user's interactions with the system, the NL server logs are synchronised at the beginning of each user trial by the experimenter who triggers a function which aligns the inputs with the DAT.

The users were asked to complete a series of tasks which involved selecting and applying fabrics to items in the virtual room. Before the trials were started, the experimenter outlined the system's capabilities, but deliberately did not instruct users on how to interact with the system. This was to avoid priming to one particular mode of operation. Priming is a key issue in Wizard of Oz experiments; they are designed to collect 'typical' behaviour of the user, and so must avoid pre-conditioning this behaviour. The experimenter provides assistance only when absolutely necessary, and even then must avoid directly instructing the user on how to interact with the system, but give more indirect help such as rephrasing an error message.

The users then began a simple 'warm-up' task, followed by up to nine main tasks. There was no pressure to complete them all; working at their own pace users completed the tasks sequentially until they ran out of time. We chose task-based trials rather than allow the user to randomly browse as we wanted to elicit a wide range of user behaviour. The tasks required users to find and apply fabrics and wallpapers according to a number of criteria, including colour, pattern and fabric name. A number of the tasks required users to select their own fabrics and wallpaper constrained only by a given colour scheme. Selection of materials according to a budget also played a role; when users overspent, they had to select an alternative, cheaper fabric. Again, to avoid priming, the tasks were described using minimal text and mostly consisted of a colour screen shot of the room in the fabrics that we wanted users to select.

The Wizard of Oz trials produced eleven sets of interactions from the 11 subjects, each lasting approximately 40 minutes. Only one of the users suspected that the system might not be fully automatic, although other workers have reported that people are easily fooled! The interactions were recorded both on video, and as a timestamped log of events such as when the user touches the screen. The experimenter conducted a post-trial debriefing interview and questionnaire which assessed the user's reaction to the system. Orthographic transcription of the audio has yielded a database of about 1200 user utterances, which is currently being used for robust parsing and grammar learning experiments. Further work is required to produce a unified database with transcribed speech and timed touch events.

The interviews and questionnaires gave much information about the users' perception of the system. In brief summary, the majority of subjects liked being able to use speech combined with touch; only one thought that using existing 'computer' technology (i.e. mouse, keyboard) would be preferable. Some subjects did not fully grasp the metaphor used - a shop assistant that you could talk to naturally - but were constrained by expectations of using desktop computers. In terms of using touch and/or speech modalities, two subjects consistently used pointing only, three subjects did not point at all to items in the virtual world and instead used speech, and three extensively used implied reference, for example, "Show me some striped wallpapers" followed by "try this one" <user touches palette>.

Analysis of the videos highlighted the limitations of the fabric descriptors and comparatives understood by the system; users wanted to ask for "wider stripes" or "paler material" and subsequently had difficulty selecting the fabric or wallpaper that they wanted. Users' reaction to the virtual assistant was useful in that it showed that prompts, in particular error messages, need to be carefully crafted in order to be understood and accepted. It appears that maxims such as only giving enough information and not being overly verbose are applicable in this domain.
