Living With Agents

How do Agents work?

There are several different types of agent system, [1]; some are relatively insular programs whose role is to interact with people, which tend to be known as Personal Agents. There are also agents that exist in societies and must collaborate with both people and other agents to achieve their objectives, these tend to be known as Collaborative Agents. These two species of agent emphasise different technologies: personal agents must analyse and learn user preferences, while collaborative agents communicate with and understand each other.

Personalisation and Learning

The increasing volume of online information has motivated the personalisation of agent technology, as an agent that possesses a user profile can ensure it presents only appropriate information to its user [2]. A key factor in personalisation is how the profile is compiled and adapted. Typically, when a user marks a document as interesting (or uninteresting), or the user visits a particular Web page, an agent analyses the page to determine what feature(s) caused the user to be interested (or disinterested). This information is used to update the user's profile with the features that categorise the (un)interesting pages.

Profiling technology can be applied to a vast array of applications and services including targeting content and advertisements, planning travel and leisure activities, assisting in e-commerce transactions, selecting insurance and financial investments, and the like. There are also more immediate benefits in the form of personalised search and retrieval services. The automatic adaptation of profiles means that the longer the agents are used, the more accurate their models of their users. As users are relieved from the tedium of manually updating profiles, and, as secure and trusted standards for exchanging personal information mature, we would expect opportunities to provide personalised services to enable individuals, groups and organisations to flourish in the global information world.

Communication and Understanding

Imagine there is a software equivalent of a travel agent on a server. You would like to arrange a holiday, but because the server is remote you lack a direct means of interaction. No problem surely, the agent is on the Internet so you should be able to communicate by sending electronic messages. Well, almost. There are several obstacles to this type of interaction. Firstly, both parties must use a common transport protocol, this will enable messages to be sent by one party and received by the other; this connection is represented by the pipe in Figure 1. But we're in luck, as there is a ready solution in the form of the TCP/IP protocol, the de facto standard for transferring information across the Internet.

The next problem is that both you and the travel agent must converse in the same communication language. Currently, the lingua franca of the Internet is the Hypertext Mark-up Language (HTML), whose standard format enables browser software to interpret pages on the Web. However, HTML Web pages were designed for presentation of information for human perusal, rather than the communication of queries, answers and travel booking instructions. Hence the first technical challenge is deriving a language that both parties can speak, and which is rich enough to represent a dialogue like a holiday reservation.

Fortunately solutions exist; several common communication languages have been created that specify the valid instructions, assertions, requests, etc, that are supported, and the syntax that is used [3]. The most widely used are KQML (Knowledge Query and Manipulation Language) and the FIPA ACL (Agent Communication Language).

For an initiator to make a request from a respondent there must be a means of transmitting the request. For both parties to understand one another, their messages must be in a common language that is grounded in a shared ontology. Once a message is received, the respondent can use its knowledge of the ontology to translate the request, e.g. into a query of its local database.

So both you and the travel agent are able to exchange messages, but there is another problem. You must both agree on common definitions of the travel-related concepts used in the conversion. These concepts form what is known as an ontology, and the lack of common definitions is known as the ontology problem, and is the most challenging obstacle to widespread interoperability of heterogeneous, distributed co-operating systems. Without an ontology it is impossible to ask questions about concepts like journey legs, airlines and types of fares. Fortunately this problem can be solved by creating a domain-specific ontology, like those defined in XML DTDs (Document Type Definitions).
